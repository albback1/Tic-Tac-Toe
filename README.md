# Tic-Tac-Toe на Go

Backend для игры в крестики-нолики, реализованный на Go.

Проект создан не только для реализации игровой механики, но и для практики построения приложения с архитектурой, приближенной к production-проектам: с разделением на слои, интерфейсами, dependency injection, потокобезопасным хранилищем и отдельными моделями для domain, datasource и web-слоёв.

## О проекте

Игра работает по принципу:

```text
Клиент → HTTP API → Business Logic → Repository → Storage
```

Пользователь отправляет свой ход, после чего приложение:

1. получает текущую игру по UUID;
2. валидирует ход пользователя;
3. проверяет корректность текущего состояния игрового поля;
4. проверяет состояние игры;
5. рассчитывает ход компьютера с помощью алгоритма **Minimax**;
6. сохраняет обновлённое состояние игры;
7. возвращает клиенту игровое поле с ходом компьютера.

Приложение поддерживает **несколько игр одновременно**.

## Стек

* **Go**
* **net/http** — HTTP-сервер и обработка запросов
* **uber/fx** — dependency injection
* **sync.Map** — потокобезопасное хранение текущих игр
* **UUID** — идентификация игровых сессий

## Архитектура

Проект разделён на несколько независимых слоёв

### Domain

Содержит предметную область игры и не зависит от HTTP или конкретного способа хранения данных.

Основные компоненты:

* модель игрового поля — целочисленная матрица `3x3`;
* модель текущей игры с UUID и игровым полем;
* интерфейс игрового сервиса;
* игровая логика;
* алгоритм Minimax;
* валидация ходов;
* проверка окончания игры.

### Datasource

Отвечает за хранение состояния игр.

Для хранения используется потокобезопасная коллекция `sync.Map`, благодаря чему несколько игровых сессий могут обрабатываться одновременно.

Слой содержит:

* структуру-хранилище;
* datasource-модели;
* repository;
* мапперы между domain и datasource моделями.

Repository предоставляет операции:

```text
SaveGame
GetGame
```

### Web

Отвечает за взаимодействие с клиентом через HTTP API.

Используется стандартный пакет Go `net/http`.

Web-слой содержит:

* HTTP handler;
* DTO для запросов и ответов;
* мапперы между web и domain моделями;
* маршруты.

Основной endpoint:

```http
POST /game/{UUID}
```

Клиент отправляет свой ход, а в ответ получает текущее состояние игры после хода компьютера.

Некорректные ходы и изменения уже сделанных ходов обрабатываются с возвратом ошибки и описанием причины.

### DI

Для построения графа зависимостей используется `uber/fx`.

Зависимости приложения организованы следующим образом:

```text
Storage
   ↓
Repository
   ↓
Game Service
   ↓
HTTP Handler
   ↓
Route
```

Хранилище создаётся как singleton и передаётся в repository через dependency injection.

## Игровая логика

Основная часть проекта — реализация логики крестиков-ноликов.

### Валидация хода

Перед выполнением хода сервис проверяет:

* существует ли игра;
* является ли ход допустимым;
* изменена ли только одна клетка;
* не была ли изменена уже занятая клетка;
* соответствует ли новое значение клетки ходу пользователя;
* не были ли изменены предыдущие ходы.

Таким образом, клиент не может просто отправить произвольно изменённое игровое поле.

### Minimax

Для выбора хода компьютером используется алгоритм **Minimax**.

Алгоритм перебирает возможные состояния игрового поля и оценивает их исход/

На основании этих оценок компьютер выбирает оптимальный ход.

## API

### Сделать ход

```http
POST /game/{UUID}
Content-Type: application/json
```

Пример запроса:

```json
{
  "row": 1,
  "col": 2
}
```

Пример ответа:

```json
{
  "id": "game-uuid",
  "field": [
    [1, 2, 0],
    [0, 1, 0],
    [2, 0, 0]
  ]
}
```

Обозначения:

```text
0 — пустая клетка
1 — крестик
2 — нолик
```

При некорректном ходе API возвращает HTTP-ошибку с описанием причины.

## Запуск

Клонировать репозиторий и установить зависимости:

```bash
go mod download
```

Запустить приложение:

```bash
go run ./cmd
```

После запуска сервер доступен по адресу:

```text
http://localhost:8080
```

## Цель проекта

Основная цель проекта — на практике разобраться не только с Go и алгоритмами, но и с проектированием приложения с разделением ответственности.

В проекте отдельно выделены бизнес-логика, HTTP-взаимодействие и хранение данных. Компоненты связаны через интерфейсы и dependency injection, что позволяет изменять отдельные части приложения без жёсткой зависимости между слоями.
